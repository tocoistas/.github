## Sobre Este Repositório

Este é o **repositório institucional oficial** da **Igreja de Nosso Senhor Jesus Cristo no Mundo**, também conhecida como **Os Tocoístas**, gerido pelos Anciãos Conselheiros da Direcção Central.

Este espaço foi criado para **centralizar, organizar e partilhar** o código-fonte, a arquitectura técnica e a documentação de todos os projectos de software desenvolvidos em prol da Igreja e da sua comunidade global. É aqui que a fé encontra a tecnologia — onde cada linha de código é um acto de serviço e cada _commit_ é uma contribuição para a obra do Senhor.

> **Transparência, Inovação e Serviço** são os pilares que guiam cada projecto alojado nesta organização.

Os objectivos principais deste repositório são:

| Objectivo | Descrição |
|-----------|-----------|
| **Transparência** | Tornar o desenvolvimento dos projectos visível e auditável por toda a comunidade |
| **Colaboração** | Reunir talentos de TI dispersos por todo o mundo numa missão comum |
| **Inovação** | Promover o desenvolvimento de soluções modernas e adequadas às necessidades da Igreja |
| **Continuidade** | Garantir que o conhecimento técnico não fique concentrado em poucos, mas seja partilhado |
| **Excelência** | Elevar os sistemas digitais da Igreja a um padrão de qualidade que honre a nossa missão |

## Áreas de Contribuição

A sua experiência pode fazer a diferença em uma ou mais das seguintes frentes:

### 🏗️ Arquitectura e Desenho
Ajude-nos a projectar sistemas robustos, escaláveis e seguros. Colabore na definição de padrões de arquitectura, na revisão de decisões técnicas e na elaboração de diagramas e especificações que guiem o desenvolvimento a longo prazo.

### 💻 Desenvolvimento e Construção
Participe na escrita de código limpo, testado e eficiente. Crie novas funcionalidades, implemente interfaces de utilizador intuitivas, construa APIs e integre os sistemas entre si.

### 🔧 Manutenção e Optimização
Contribua para a melhoria contínua dos sistemas já existentes. Corrija _bugs_, melhore o desempenho, refactore código legado e garanta a estabilidade e a disponibilidade dos serviços.

### 📋 Análise e Documentação
Auxilie no levantamento de requisitos junto das equipas da Igreja, elabore especificações funcionais e técnicas claras e produza documentação acessível que permita a novos voluntários integrar-se rapidamente em qualquer projecto.

### 🔒 Segurança e Qualidade
Reveja o código em busca de vulnerabilidades, implemente boas práticas de segurança, escreva testes automatizados e contribua para a definição de políticas de qualidade que protejam os dados dos membros e a reputação da Igreja.

## Como Colaborar — Guia Passo a Passo

### 1. Crie a sua Conta no GitHub
Se ainda não tem uma conta, registe-se gratuitamente em [github.com](https://github.com).

### 2. Apresente-se no Canal de Comunicação
Antes de começar a contribuir, junte-se ao nosso **Canal Oficial de Colaboradores no WhatsApp** (ver secção [Canal de Comunicação](#canal-de-comunicação)) e apresente-se brevemente: o seu nome, a sua localização, a sua área de expertise e a sua motivação para colaborar.

### 3. Explore os Repositórios
Aceda à organização em [github.com/tocoistas](https://github.com/tocoistas) e explore os repositórios disponíveis. Leia os ficheiros `README.md` e `CONTRIBUTING.md` de cada projecto para compreender o seu propósito e o estado actual.

### 4. Escolha uma Tarefa
- Consulte o separador **Issues** do repositório que lhe interessa.
- Procure _issues_ com a etiqueta `good first issue` se for a sua primeira contribuição.
- Comente na _issue_ para indicar que pretende trabalhar nela, evitando duplicação de esforço.

### 5. Faça um Fork e Clone o Repositório
```bash
# Faça o fork através da interface do GitHub, depois clone o seu fork:
git clone https://github.com/SEU-UTILIZADOR/NOME-DO-REPOSITORIO.git
cd NOME-DO-REPOSITORIO

# Adicione o repositório original como remote "upstream":
git remote add upstream https://github.com/tocoistas/NOME-DO-REPOSITORIO.git
```

### 6. Crie um Branch para a Sua Contribuição
```bash
# Mantenha o main sempre sincronizado com o upstream:
git checkout main
git pull upstream main

# Crie um novo branch descritivo para a sua tarefa:
git checkout -b feat/descricao-curta-da-tarefa
# ou para correcção de bugs:
git checkout -b fix/descricao-do-bug
```

### 7. Desenvolva a Sua Contribuição
- Escreva código claro, legível e bem testado.
- Siga as normas de desenvolvimento descritas abaixo.
- Faça _commits_ frequentes e com mensagens descritivas (veja [Normas de Desenvolvimento](#normas-de-desenvolvimento)).

### 8. Submeta um Pull Request
```bash
# Envie o branch para o seu fork:
git push origin feat/descricao-curta-da-tarefa
```
- Aceda ao GitHub e abra um **Pull Request** do seu branch para o branch `main` (ou o branch indicado) do repositório original.
- Preencha o formulário do PR com uma descrição clara do que foi feito, o problema que resolve e, se aplicável, capturas de ecrã ou instruções de teste.
- Associe o PR à _issue_ correspondente com a sintaxe `Closes #NúmeroDaIssue`.

### 9. Revisão e Aprovação
- Um membro da equipa de manutenção irá rever o seu PR e poderá solicitar ajustes.
- Responda aos comentários de forma construtiva e faça as alterações necessárias.
- Após a aprovação, o PR será fundido (_merged_) no projecto.

## Regras e Código de Conduta

Todos os colaboradores desta organização comprometem-se a observar os seguintes princípios:

### ✝ Respeito e Fraternidade
Este repositório é um espaço de serviço à comunidade da Igreja. Toda a comunicação — em _issues_, _pull requests_ ou comentários — deve ser **respeitosa, construtiva e fraterna**. Não serão toleradas linguagem ofensiva, desrespeito ou qualquer forma de discriminação.

### 🤝 Colaboração, não Competição
O objectivo comum é o avanço dos projectos da Igreja. Valorize as contribuições alheias, ofereça ajuda aos colegas menos experientes e partilhe o seu conhecimento generosamente.

### 🔐 Confidencialidade e Protecção de Dados
- **Nunca** submeta para o repositório credenciais, senhas, chaves de API ou dados pessoais de membros da Igreja.
- Todos os dados sensíveis devem ser geridos através de variáveis de ambiente e ficheiros `.env` (não versionados).
- A protecção da privacidade dos membros é uma responsabilidade partilhada por todos os colaboradores.

### ✅ Qualidade e Responsabilidade
- Não submeta código que sabe estar incompleto ou com erros conhecidos sem o indicar claramente.
- Teste sempre o seu código antes de abrir um Pull Request.
- Mantenha a documentação actualizada a par das alterações de código.

### 📜 Licença e Propriedade Intelectual
Todo o código submetido deve ser compatível com a licença do projecto em questão. Ao submeter uma contribuição, o colaborador confirma que possui os direitos necessários para o fazer e que concorda com os termos da licença do projecto.

## Fluxo de Trabalho (Git Flow)

Todos os repositórios desta organização seguem uma adaptação do **Git Flow**:

```
main          ← Branch de produção (código estável e aprovado)
  └── develop ← Branch de integração (desenvolvimento activo)
        ├── feat/nome-da-funcionalidade
        ├── fix/descricao-do-bug
        ├── docs/actualizacao-de-documentacao
        └── refactor/nome-do-componente
```

- **`main`** — Contém apenas código testado e aprovado. Nenhum colaborador escreve directamente neste branch.
- **`develop`** — Branch principal de desenvolvimento. Os PRs são submetidos para aqui, salvo indicação em contrário no repositório específico.
- **Branches de funcionalidade** — Criados a partir de `develop` para cada nova tarefa, e eliminados após o _merge_.

## Normas de Desenvolvimento

### Mensagens de Commit
Utilize o padrão **Conventional Commits** para manter o histórico legível:

```
tipo(âmbito): descrição curta em minúsculas

[corpo opcional: explicação mais detalhada]

[rodapé opcional: referência a issues, breaking changes]
```

| Tipo | Quando usar |
|------|-------------|
| `feat` | Nova funcionalidade |
| `fix` | Correcção de bug |
| `docs` | Alterações na documentação |
| `style` | Formatação, ponto e vírgula em falta, etc. |
| `refactor` | Refactorização de código sem alterar funcionalidade |
| `test` | Adição ou correcção de testes |
| `chore` | Tarefas de manutenção, dependências, CI/CD |

**Exemplos:**
```
feat(auth): adicionar autenticação por dois factores
fix(portal): corrigir erro de renderização no menu mobile
docs(readme): actualizar guia de instalação
```

### Código
- Siga as convenções de estilo definidas em cada repositório (geralmente aplicadas via _linter_ e _formatter_ automáticos).
- Escreva testes para as funcionalidades que implementa.
- Mantenha as funções pequenas e com uma única responsabilidade.
- Prefira clareza à inteligência — o código será lido e mantido por outros voluntários.
